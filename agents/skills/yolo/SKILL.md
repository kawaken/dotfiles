# Kawaken Personal Ship

個人リポジトリ向けの出荷フローを一気通貫で実行する。仕事リポジトリの標準フローには使わない。

## 実行条件

- このスキルが明示的に呼び出された場合だけ実行する。通常の「PRして」「マージして」では自動選択しない
- Codexでは `$yolo`、Claude Codeでは `/yolo` として明示的に呼び出す
- `git`、GitHub CLI (`gh`)、リモートへのpush権限が必要
- AutoMergeを優先する。AutoMergeが無効・権限不足・リポジトリポリシーで利用不可の場合、手動マージへ勝手に切り替えず停止する

## フロー

1. `git status`、現在のブランチ、リモート、変更差分を確認する。既存の変更を勝手に捨てず、今回の作業に関係するファイルだけを対象にする
2. デフォルトブランチ上で作業している場合は、リポジトリやユーザーレベルの規約に従った作業ブランチを作成する。規約がなければ、短く説明的なフラットな名前にする
3. リポジトリの指示と実装内容に応じて、テスト・型チェック・lintなど必要な検証を実行する。利用可能な検証がない場合はその旨を記録する
4. 変更を確認し、関係するファイルだけをstageしてcommitする。commitメッセージは変更内容を端的に表す
5. ブランチをリモートへpushする。upstreamがなければ設定する
6. ready-for-reviewのPRを作成する。ユーザーがdraftを指定した場合だけdraftにする
7. リポジトリで許可されているマージ方式を確認し、通常はsquashを優先してAutoMergeを有効化する。PR作成時点でCIが未完了でもAutoMergeを先に設定する
8. CIを監視する。保留中は完了まで待ち、失敗したら失敗ジョブとログを確認して原因を特定する
9. コードや設定の修正で直せる失敗なら、同じブランチで修正・検証・commit・pushを行い、CI監視へ戻る
10. CI成功後、PRのstateとmergedAtを確認する。AutoMergeによるマージ完了まで追跡し、完了したらPR URL、commit、CI結果を報告する

## CI失敗時の判断

- コード変更で解決できる失敗は、原因を説明できる修正を行って再実行する
- flaky test、外部サービス障害、secret・権限不足、必須レビュー、merge conflictなど、コードだけで解決できない場合は停止して必要な対応を報告する
- 同じ原因で2回連続して失敗した場合は、無理にループせず停止してログと仮説を報告する
- CIが成功していない状態で手動マージしない
- AutoMergeが設定済みでも、最後に必ずPRが実際にmergedになったことを確認する
